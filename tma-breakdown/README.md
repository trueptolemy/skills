# tma-breakdown: explain a score gap with TMA

A Claude Code skill that breaks the throughput score gap between two
configurations (typically a VM and bare metal) into Intel TMA / top-down
nodes from EMON summary CSVs. It is based on the method document
*Break Down Performance Gap into Topdown Metric*.

The agent:
1. asks for the workload name, the baseline case and the score of every case;
2. checks whether the method applies: TMA completeness, multiplexing,
   frequency, utilization and beta, collection scope, and EMON-window
   consistency (CPI vs score, window length vs 1/r, instruction mix);
3. computes the top-level and sub-node breakdown in points of score gap;
4. cross-validates every significant node with independent EMON metrics and
   events (for example, a DTLB gap is checked against page-walk counts,
   cycles per walk and walk-active cycles);
5. writes a Markdown report with the tables and evidence-based hypotheses
   into the current directory (`tma-breakdown-<workload>.md`, overwritten on rerun).

## Layout

```
SKILL.md                      workflow the agent follows (intake, gate, compute, interpret, deliver)
README.md                     this file
scripts/
  tma_breakdown.py            inspect | report  (Python 3 standard library only)
reference/
  method.md                   score model, breakdown identity, sub-node weights, noise band, window decomposition
  applicability.md            every check, its thresholds and what to do when it fails
  interpretation.md           evidence patterns (EPT walks, exit-induced front-end pollution, window mismatch, ...)
  crosscheck-rules.json       TMA node -> EMON evidence (metric / event per instr / per cycle / ratio)
tests/
  selftest.sh                 offline tests on synthetic EMON data (optional real-data smoke test)
  test_tma_breakdown.py
```

## The report

`report` writes a Markdown file with these sections. Sections marked
*agent* are completed by the agent; everything else is generated by the
script and must not be edited by hand.

| section | content |
|---|---|
| 1. Verdict | APPLICABLE / APPLICABLE WITH CAVEATS / NOT APPLICABLE, every WARN, FAIL and ASK check in one line, and a short summary of the findings (*agent*) |
| 2. Inputs | each case with its EMON file and column, its score and the matched score label, its EMON window length, and its role (baseline or compared); the parameters used |
| 3. Applicability checks | one row per check, with the value of every case, the status and a note (see `reference/applicability.md`). Checks: TMA presence, TMA sum and TMA version; multiplexing; scores; frequency; utilization / beta; CPI consistency; window coverage; instruction mix; uncore and DDR; kernel share; and the user's confirmations, which are verified against the data where possible |
| 4. Score model | per compared case: score gap, r, beta (used, its source and the EMON estimate), gap_virt, the EMON CPI ratio, alpha as given, and alpha as implied by the EMON CPI |
| 5. Top-level breakdown | Frontend, Bad_Speculation, Backend and Retiring gaps in points of score gap. They add up to the score gap together with gap_virt and the residual. `~` marks a value inside the score-noise band |
| 5.1 Decomposition | each level-1 gap split exactly into d_i, the per-instruction change between the EMON windows, plus the alpha term (hypervisor instructions) plus the window term (score-vs-EMON inconsistency). Conclusions are robust where both views agree |
| 6. Sub-node breakdown | the TMA tree: each node's ratio in every case, its weighted gap (a share of the score gap; children add up to their parent) and its unweighted gap (ranking only). `‡` marks overlapping cycle-based nodes |
| 7. Cross-validation | 7.1 node summary: supports, contradicts and flat counts, a status (corroborated, weakly supported, mixed, contradicted, children diverge, no signal) and d per node. 7.2 evidence rows: BM and VM values, VM/BM ratio, the expected direction and a verdict. 7.3 context metrics: CPI, supervisor shares, far branches, window length, SMT activity, workload-intrinsic rates. 7.4 automatic observations |
| 8. Hypotheses | numbered hypotheses, each with its nodes, its evidence rows, the mechanism (conjecture), a confidence level and a confirming or refuting experiment (*agent*) |
| 9. Derived evidence and open questions | extra evidence the agent computed from raw EMON rows, labelled "derived" with formula and values; questions for the user (*agent*) |
| 10. Caveats | the limits of the method |

`--json FILE` writes the same results (model, checks, breakdown, cross-check)
in machine-readable form.

## Command line

```bash
S=~/.claude/skills/tma-breakdown/scripts
python3 $S/tma_breakdown.py inspect --emon emon.csv
python3 $S/tma_breakdown.py report --emon emon.csv --scores scores.csv \
    --workload 520.omnetpp_r --baseline bm \
    --beta '4k-nothp vm=1' --beta '2m vm=1' \
    --confirm throughput=yes --confirm host_side_tma=yes \
    --confirm same_phase=unknown --confirm cpu_saturated=yes
```

Input data:
- **EMON:** one CSV with several case columns, or `--case NAME=file.csv[@COLUMN]` per case.
- **Scores:** a CSV with case names in the header and a `score` row. Column
  names may carry extra text after the case name. Alternatively, use
  `--score CASE=VALUE`.
- **Direction:** `--direction lower` for elapsed-time metrics.
- **Optional:** `--alpha CASE=VALUE` (perf `instructions:H` / `instructions:G`)
  feeds only the consistency check. `--json` writes machine-readable results.

The verdict is NOT APPLICABLE when any check fails. In that case the
breakdown is not computed unless `--force` is given.

## Requirements and limits

- Python 3.8 or later; no third-party modules.
- EMON summaries from the EDP metric post-processor with `metric_TMA_*(%)`
  rows. Cross-check rules use SPR/EMR/GNR event names; missing evidence shows
  as `missing`.
- The method needs a throughput score proportional to 1/time, saturated CPUs,
  equal frequency and utilization (or a measured beta), and VM-case TMA
  collected on the host over all cycles. See `reference/applicability.md`.
- The breakdown is an accounting identity, not a causal model. Hypotheses in
  the report must be confirmed by experiments.
